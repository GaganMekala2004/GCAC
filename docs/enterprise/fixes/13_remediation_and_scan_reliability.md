# Remediation and scan reliability

Patch proposals now preserve unified-diff lines, including blank context and no-newline markers. Git checks the exact patch against the isolated worktree before an approval request is created. Invalid proposals receive at most two regeneration attempts; all regenerated proposals pass the same scope and suppression checks. Approval remains bound to the final exact diff and base revision. A failed proposal never becomes executable through a full-file replacement or fuzzy patch application.

## Follow-up: malformed model hunk metadata

The first retry-only change did not resolve the observed failure. All three real proposals from attempt `att-1-f819dd57` used incorrect hunk counts, two used incorrect source line positions, and all omitted EOF metadata for a source file with no final newline.

The proposal step now reconstructs an edit only when every old hunk matches exact, unique source text and hunks are ordered and non-overlapping. A missing EOF marker is recoverable only when all old text matches the source suffix exactly; the original final-newline convention is preserved. No whitespace approximation or guessed replacements are allowed. Ambiguous, missing, out-of-scope, unsupported, or context-free edits remain rejected. Git generates the final diff from local temporary before/after files; the isolated source stays unchanged until approval. Git then validates that diff, and the approval digest binds to the generated diff. Canonicalization records input/output digests in the audit chain.

Verification: all three actual failed proposals now pass Git validation. Applying the reconstructed first proposal to a disposable payments-api copy passed the genuine local-container test (1/1, exit 0); the originating `SEC-005` rule returned zero matches on the target. This smoke test and scanner result are not proof of full SQL dataflow safety or final remediation closure. All 25 regression suites passed, including malformed counts, missing EOF metadata, CRLF preservation, ambiguous context, source mismatch and additional-file rejection.

The DES finding remains an architectural migration rather than an automatic DES-to-AES substitution. Its decision now explains the missing compatibility contract and lists migration/review steps. Crypto classification also uses algorithm word boundaries rather than the substring `des`, avoiding unrelated classifications such as deserialization.

## Follow-up: incomplete old context and approval visibility

Attempt `att-1-a6583e9c` omitted the existing `using var cmd` statement from its old hunk context while adding a new one. That proposal must remain rejected: its old source does not exist. Reconstructing it by guessing which omitted lines to delete would be unsafe.

The model now returns JSON `edits` with exact `oldText`/`newText` fragments instead of writing a diff. Old fragments must exist uniquely and edits must not overlap. Git generates and validates the final diff before the same scope, suppression, baseline and approval gates. Rejection feedback includes the redacted rejected response and the exact matching requirement. Legacy unified-diff responses still undergo conservative validation.

Valid Stage 4 results expose the existing `/approve <finding>` instruction and a clickable chat button. The button is bound to the proposal's run ID and SHA-256 and delegates to the existing approval flow. Stale buttons are rejected. The webview's approval card remains limited to a valid awaiting-review stage. Proposal failures explicitly explain why no approval request exists; architectural-review referrals also explain that they are not Stage 4 code approvals. Execution failures are no longer labeled as post-fix validation failures when tests never ran.

Run state is a changing lifecycle artifact. A legitimate `RunStateManager` write now updates its manifest digest atomically after verifying the entire pre-write evidence package. It records the previous state digest and trusted revision. A previously mismatched package is never silently repaired, and other artifacts are never rehashed by a state save. Historical mismatches remain flagged until a fresh evidence bundle is deliberately generated by the workflow. Tests cover legitimate state transitions, direct state modification and unrelated evidence modification.

## Follow-up: repeated approval and final gate persistence

A repeated Stage 4 approval after application now returns the existing result without executing the pipeline or mutating its state/evidence. The execution layer retains replay prevention for application writes; the user-facing duplicate submission is idempotent. Concurrent submissions are also intercepted in the UI. Pending Stage 8 results persist their stage as `awaiting_review`, so Sync Status and reload continue to expose the sign-off card. Chat `/approve` responses at Stage 8 now offer a separate run/diff-bound final-sign-off button; an old Stage 4 button cannot authorize Stage 8.

After an applied patch fails later execution, error handling preserves the historical consumed approval and applied diff instead of clearing them. Exception diagnostics are written beneath `attempts/<attempt>/execution-failure/`, so they do not overwrite sealed trace or validation artifacts. Existing historically corrupted runs are retained as evidence; they require a fresh proposal rather than reconstructed approval records.

C# candidate generation also rejects newly introduced duplicate ordinary `var` declarations within a block. This focused guard catches the observed duplicate `cmd` before approval; it does not replace compiler tests or claim general semantic correctness. Invalid proposals receive ordinary correction feedback. Loop/using-statement implicit scopes are excluded from this guard.

## Reviewed crypto migration, visible chat continuation, and publication

Fresh runs recompute remediation routing instead of reusing a historical manual-review decision indefinitely. A DES migration can proceed after the user explicitly reviews a source-SHA-bound contract through **Review crypto migration contract** in chat. The supported contract preserves the method signature but requires a 32-byte key, unique caller-supplied 12-byte nonce, and versioned AES-GCM envelope `[1][nonce12][tag16][ciphertext]`. The user must confirm that legacy ciphertext need not be preserved and caller changes are authorized. A source change invalidates that contract. This review permits proposal generation only; the actual diff still requires separate Stage 4 approval. Legacy-data compatibility and unsupported primitives remain blocked rather than receiving guessed migrations.

After approval, crypto migrations run an owned xUnit contract harness in a disposable repository copy, using the approved container runner. It checks envelope format, round trip, tamper rejection, wrong key, and invalid key/nonce lengths. The harness and real result are persisted as evidence. The original smoke suite alone cannot satisfy the migration: the result must include the additional three discovered tests. Repositories without a supported test project remain unverified. Local verification of this harness passed 4/4 tests with a conforming AES-GCM fixture; the original DES implementation executed 4 tests and failed 2. These fixtures do not constitute approval or remediation of the user's DES source.

Chat approval buttons now open explicit `/approve` or `/final-approve` participant turns with bound run/diff IDs, so subsequent stage events appear in Copilot chat. Copilot is used through the VS Code language-model API for classification, source analysis, proposal generation and independent review. The extension and approved container runner perform filesystem edits, tests and scanner execution; this is not native Copilot Agent tool execution. Documentation is generated deterministically. Only explicit approval commands grant consent; remediation text mentioning `signoff` or quoting `/final-approve` cannot grant approval.

Stage 9 is persisted as completed after closure succeeds. Older already-closed runs with an erroneous active Stage 9 marker are normalized for display without changing test outcomes. Closure remains in progress until documentation and any configured publication complete; publication failure cannot claim a completed workflow or erase passing test evidence.

For GitHub repositories, a new Stage 8 publication plan records the exact owner/repository, local origin default branch, generated branch, run ID and reviewed diff SHA. Final confirmation explicitly authorizes pushing that isolated branch and creating a **draft** PR. VS Code GitHub authentication supplies the token; no token is written into command arguments, source files or evidence. Only approved files and verified post-apply source bytes can be committed. The GitHub REST response must include a valid PR number/URL. No merge or force-push is performed. Retries reuse the same remote PR or an unchanged publication commit. Remote publication is tested with mocked GitHub services and real temporary Git commits; no live GitHub PR was created during implementation.

Without a supported GitHub `origin` and locally recorded `origin/HEAD`, publication is **NOT_CONFIGURED**. Final confirmation then offers local evidence closure only and explicitly states that no PR will be created. The payments-api sample currently has no origin remote. Adding a remote later does not retroactively authorize publishing an already-closed run: prepare a new reviewed publication plan. GitHub errors remain errors, never fabricated PR success.

API references: https://code.visualstudio.com/api/extension-guides/ai/language-model and https://docs.github.com/en/rest/pulls/pulls

## Candidate compilation and reproducible correction

Git applicability alone is insufficient proposal validation. Every C# candidate now runs `DOTNET_BUILD` through the approved execution gateway in a disposable copy with networking disabled. A successful actual build is required before Stage 4. Compiler diagnostics such as `CS0117` (invented `CipherMode.GCM`) and `CS0103` (missing `SanitizeReceiptId`) are fed back to the model for bounded correction. A missing compiler/container is a prerequisite failure, never a successful proposal. Reviewed crypto candidates also run their contract harness in the disposable copy before approval; normal post-approval tests and originating-scanner validation remain mandatory and run separately.

After three unsuccessful model proposals, narrowly recognized .NET source patterns can use a deterministic repair proposal. Supported shapes are the observed two-field SQL concatenation with an existing command, a literal Windows batch invocation with an identifier argument, and the exact DES method governed by an explicitly approved no-legacy-data AES-GCM contract. SQL bindings reuse the original command; batch identifiers are constrained to 1–64 ASCII letters/digits/underscores/hyphens and passed through `ArgumentList`; AES-GCM uses the real framework API and reviewed envelope. Unknown source patterns receive no guessed fallback. Recipe use is logged and every candidate passes the same scope, compilation, review and runtime gates. The Windows batch recipe's identifier restrictions are visible behavior changes requiring diff review; Linux tests verify input rejection, not execution of a Windows batch script.

Real Docker reproduction rejected the two recorded broken proposals with their original compiler errors. All three corrected pattern proposals compiled successfully. A disposable combined fixture passed seven runtime tests: the controller smoke test, three hostile receipt identifiers, and three reviewed crypto-contract tests. No source in the user's main checkout was changed by these reproductions.

`PATCH_INVALID` failures now expose **Review Failure / Revise Fix**, rather than only a disabled blind retry. Revision retains failure diagnostics and always requires fresh approval of the corrected diff. Compilation does not grant authorization to apply the candidate to the authoritative isolated branch.

Fresh runs move prior top-level evidence and snapshots into a separate `runs/previous-...` generation before initializing current state. Prior mismatches remain detectable in their original archived manifest. Failure before an approval proposal seals an honest new failure bundle. Shared historical Markdown cannot supply a different run's patch or test outcomes; explicit current-run nulls override fallback report content. This prevents a failed current proposal from displaying a previously approved diff or reusing a previous run's manifest.

An **Open actual remediated source** chat action opens the source that Stage 5 really changed in its isolated worktree. Final publication commits those approved bytes and pushes that branch to a new GitHub draft PR after explicit confirmation. The user's main checkout is updated through the normal PR merge/check-out workflow; it is not silently overwritten before review.

Rejected proposals are recorded under `remediation-output/<finding>/attempts/<attempt>/patch-proposals/` with credential redaction, a source hash, base commit, and a safe diagnostic category. Git stderr is not sent to the model because it can contain source secrets.

Manual architectural review is a first-class blocked outcome with unexecuted validation. It is persisted to canonical run state and rendered separately from test failures. Other blocked prerequisites are no longer automatically labeled as missing toolchain images. A cryptographic migration still requires a reviewed migration plan; this change does not bypass that decision.

## NuGet intelligence

Run `node scripts/refresh-nuget-advisories.js` to provision official NuGet VulnerabilityInfo data. This downloads public advisory JSON only, without uploading source or package inventories, restoring dependencies, or executing repository code. The downloader accepts only HTTPS requests to `api.nuget.org`, rejects redirects and oversized responses, handles gzip, validates all pages, and atomically replaces the snapshot after a successful complete download. A failed refresh preserves the existing file.

The snapshot is stored at `output/scans/nuget-advisories.json`, outside target repositories. It expires after 24 hours. Scans automatically refresh an existing expired snapshot; initial provisioning is explicit. A missing or expired snapshot cannot produce a clean audit. The snapshot is local TLS-fetched data, not a separately signed attestation.

For supported restored projects the scanner checks resolved direct and transitive package versions against real NuGet advisory ranges, including prerelease and four-component versions. It examines every project under a repository target and reports project/package counts and advisory freshness. Missing, outdated, unevaluated, or unsupported graphs fall back to the existing approved sandbox path. Central package management and arbitrary build imports require that sandbox path. A package cache alone is insufficient vulnerability intelligence. Advisory-dependent result caching is bypassed so advisory freshness and restored graph changes are always checked.

The text parser distinguishes NU1900/NU1905 intelligence failures from NU1901–NU1904 vulnerability detections, supports transitive table rows, and retains actual findings even when coverage or process execution fails. Missing feed access remains incomplete coverage.

Reference: https://learn.microsoft.com/en-us/nuget/api/vulnerability-info

## CodeQL

The scan controller no longer overrides every adapter with a 60-second timeout. CodeQL uses its existing five-minute timeout per extraction/analysis phase; callers can specify `timeoutMs` or `scannerTimeouts.codeql`. Timeout and cancellation terminate the CLI process tree, including dotnet/java descendants that could otherwise keep output pipes open. Each invocation uses unique temporary paths and extracts from a disposable source copy, preventing dependency restore from changing the user's source or interfering with other scanners. SARIF locations map back to the original repository. Invalid JSON, missing result arrays, and unsuccessful SARIF invocations fail validation instead of reporting complete coverage.

CodeQL C# buildless extraction can still restore dependencies. A restricted environment without usable dependencies/network access can therefore remain incomplete; increasing a timeout does not repair missing prerequisites. This must remain visible in scan results.

Reference: https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages
